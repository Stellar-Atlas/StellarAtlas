# Public notice dry run

This is an offline policy experiment beside an exact allowlisted snapshot of the existing status project. It is not connected to its monitor, D1 store, Worker schedule or HTTP handlers. Existing source bytes remain unchanged. The signed baseline and external SHA256 manifest identify the local source; the previously reported deployment revision is not independently byte-attested.

The offline fixtures exercise confirmed outage and recovery notices, duplicate suppression, cooldowns and failed delivery. Automatic posting remains disabled. The status page is the public record.

Reuse `readStatus()`'s three components and monitor-confirmed incidents. The monitor already retries each probe twice and retains sampled boundaries. This experiment adds posting confirmation only: two distinct matching samples at least 60 seconds apart, with no gap exceeding the existing public status unknown window of 180 seconds. Inferred/setup incidents, unknown observations, stale status and incomplete/truncated history cannot produce notices. No monitoring thresholds change.

Outage candidates are `origin_unavailable`, `data_unavailable` and `snapshot_unavailable`. `data_stale` is a separate sustained-freshness notice, never worded as an availability outage. It must remain reported stale over at least five minutes of fresh sampled observations. These are **draft posting rules**, including a 15-minute same-component/problem-kind cooldown; review and publish them before enablement. Five minutes is also the existing monitor's health-response age boundary, but the sustained window is an additional draft notice rule, not an assertion that publication uses that threshold. Publication readiness continues to come from the existing source. Archive-summary age alone is excluded by the real `dataReadiness()` and by an explicit archive-detail exclusion. No independent ledger-progression signal is present in these incident rows, so no such signal is fabricated.

An incident key contains policy version, component, persisted incident ID, sampled start and notice kind. One successful capture acknowledges it; duplicate events, new evaluation times and reload do not resend. A newer incident has a different key. Successful problem notices record an observation-time cooldown; failure does not acknowledge or start cooldown. A matching successful problem notice is required before recovery; two fresh healthy samples confirm recovery. Recovery bypasses problem cooldown so an outage is not left publicly unresolved. Obsolete failed outage candidates are discarded when recovery is observed. Historical closed incidents never bootstrap recovery notices.

The serializable fixture state separately retains the latest observed snapshot and successful capture acknowledgements. Older snapshots cannot send or reset state. Matching equal-time snapshots retry failures without counting as another sample; conflicting equal-time snapshots fail closed until a strictly newer snapshot arrives. Missing or unknown components break confirmation. Monitoring gaps restart sample confirmation and are not evidence of continuous physical outage or freshness delay.

Structured notice data retains ISO UTC incident sampled start, the current confirmation window's first/latest sample, sampled recovery when applicable, a fixed `https://status.stellaratlas.io/` public-record link and a `https://status.stellaratlas.io/api/status` evidence link. The short post shows observed and confirmed times with the status link; it does not repeat the full evidence window. These are check observations, not physical onset or exact downtime. Recovery matches the complete incident key, including sampled start, so a reused database ID cannot borrow an old notice acknowledgement. One recovery can resolve both availability and freshness notices for the same incident. No raw probe text, causes, private evidence references, addresses or tokens are rendered.

Only `CapturingNoticeSink` is accepted. It records bounded local objects and can simulate a rejected delivery; it has no transport. At most three notices are proposed per evaluation. Input history is capped at 1000, state acknowledgements at 2000 and sink captures at 100; exceeding a bound fails closed rather than evicting deduplication evidence. State is supplied/returned by the caller and tested through JSON reload, not installed as a durable production store. There is no queue, daemon, scheduler, credential, account setup, migration or posting integration.

The offline reducer and durable acknowledgement/concurrency boundary have passed independent source review and local tests, including accepted-but-response-lost handling. Remaining gates: approve the final policy and wording; attest the serving monitor/function and schedule source; provide authorized account/API access only in a separately scoped integration; qualify the actual database/provider contracts; and test staging delivery, rate limits, failure recovery, ambiguity reconciliation and emergency disablement before enablement. The status page remains the public record when posting is unavailable. Source acceptance does not satisfy real account, deployment or production delivery acceptance; no independent ledger-progression signal is supplied.
