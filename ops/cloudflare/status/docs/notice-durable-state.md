# Offline durable notice boundary

This is inert source, a signed child of the accepted NOTICE-001 dry run. No monitor, Worker, HTTP handler, schedule or deployment imports the adapter. The proposed SQL is retained as `test/fixtures/notice-delivery-schema.sql`. Only disposable SQLite tests apply it after the original migrations. It creates a separate control row **disabled by default**. Nothing automatically enables it, installs a schema, posts or queries a provider. No credentials, accounts or transport integration exist here.

`NoticeDeliveryStore` uses the project's D1 `prepare().bind().all()/run()` and transactional `batch()` shape. `evaluateOfflineDelivery` is an explicit offline entry point accepting only the concrete `OfflineNoticeTransport` fake. Its `instanceof` check is an API guard, not a sandbox against modified JavaScript. There is no generic live transport hook. Tests run the real accepted monitor/store with injected fake GET responses, then evaluate their status snapshots against file-backed SQLite. Existing monitor and reducer source stays byte-identical.

An atomic `UPDATE … RETURNING` elects one control-row owner. Every acquisition increments a safe-integer generation; all subsequent writes require that generation, its opaque owner token, enabled state, an unexpired lease and a non-regressed clock. Reusing a token never borrows a newer generation. Acquisition defaults to 30 seconds, permits at most one hour, and has no automatic renewal. Epoch exhaustion fails closed. The injected clock must be a trusted, consistent wall clock; this is not protection against a malicious caller changing time. Disablement increments the fence and prevents new acquisition/start/acknowledgement. It cannot retract an already invoked external operation; that operation remains potentially delivered.

Evaluation uses the unchanged dry-run reducer with a proposal-only capturing sink. Observations, high-water fingerprint, conflict state and confirmation samples persist without adding an acknowledgement. A transactional batch saves that state and up to three canonical public intents. No transport is invoked unless staging and a fenced `ready` to `sending` SQL transition succeed. Only a still-fresh proposal from the current evaluation may start; old failed intents are not drained as a blind queue after recovery. A ready identity can update its public confirmation text, retaining the same stable incident key. Sending, uncertain and acknowledged payloads are never replaced.

| Boundary or result | Durable behavior |
| --- | --- |
| Failure before staging commits | No transport; SQL batch rolls back. |
| Restart after staging, before send intent | `ready` remains eligible only if fresh evidence proposes it again. |
| Restart after `sending`, including death just before invocation | The next owner marks it `uncertain`; expiry cannot prove whether a send occurred. |
| Explicit fake `accepted` result | One batch persists acknowledged outcome, reducer acknowledgement and observation-time cooldown. Recovery can subsequently match this acknowledged problem. |
| Explicit `not_accepted` | No acknowledgement or cooldown; persist a bounded retry deadline. This classification must mean definite non-acceptance, never a generic exception or HTTP failure. |
| Explicit `rate_limited` | Same non-acceptance requirement, plus a global persisted send deadline across identities. Delay must be 1 ms through one hour. Longer/malformed delays fail closed as uncertain; no early retry is invented. |
| Exception, malformed result, accepted response lost, or SQL acknowledgement unavailable | Retain `uncertain` or fenced `sending`. Never automatically resend. If SQL committed but its reply was lost, the persisted acknowledgement still suppresses repeats. |
| Owner expires or is disabled during invocation | Old owner cannot acknowledge; the next owner conservatively retains uncertainty. |

There is **no exactly-once external delivery claim**. A provider can accept while its response is lost; even death after send-intent commit but before invocation is indistinguishable after restart. Uncertain problems cannot bootstrap recovery. No automatic uncertainty resolution or forced retry API is supplied. Later authorized reconciliation needs independent provider evidence and an explicit reviewed policy; clearing/resetting the database would destroy deduplication evidence and is not a retry strategy. The status page remains the public record.

The original draft policy is unchanged: two distinct matching samples at least 60 seconds apart; gaps over 180 seconds reset confirmation; sustained freshness requires five minutes; successful problem notices start a 15-minute observation-time cooldown, with equality suppressed; recovery bypasses that cooldown but requires the exact acknowledged incident identity. Replaying snapshots, restarting the process or retrying explicit failures does not manufacture another sample. Only the approved fixed public text/URLs, component names, incident identity and sampled UTC times enter delivery payloads. Persisted reducer fingerprints contain the accepted bounded structured projection and allowlisted probe categories, never raw diagnostic text. Transport responses/errors, provider IDs, private evidence, wallet data and credentials are not stored.

Capacity is fixed at 2,000 delivery identities, including ready, acknowledged and uncertain entries; SQL enforces this even under concurrent insertion. The reducer separately retains at most 2,000 acknowledgements and 1,000 input incidents. Each public payload is at most 4 KiB; reducer JSON at most 1 MiB; attempts saturate by blocking the 1,001st attempt. There is no eviction, automatic deletion or unbounded delivery log. At capacity a new identity aborts the whole staging transaction, preserving prior observation/acknowledgement state and all retained identities. Existing identities may still progress. Exhaustion requires operator review and a separately approved retention/reconciliation strategy; this slice deliberately favors duplicate prevention over indefinite unattended operation. Indexed key/state operations touch a table bounded at 2,000 rows; restart recovery scans only the indexed `sending` subset. The singleton reducer JSON is bounded, not an unbounded event store.

Offline verification: `node --test test/*.test.mjs` with an external preload denying fetch, HTTP, sockets and datagrams. Tests upgrade the actual original schema without changing its rows/definitions, reopen actual database files, race four worker-thread SQLite connections for ownership, inject transactional rollback and lost-commit replies, and exercise policy, retry, ambiguity, disablement and capacity. No dependency installation is required; the retained Node 22.20.0 `node:sqlite` implementation is the D1-shaped test shim. This proves SQL/adapter behavior locally, not Cloudflare deployment or provider compatibility.

Independent review of this inert source/SQL boundary and its offline persistence, concurrency and delivery-ambiguity tests is complete. Remaining gates: attest serving monitor/function and schedule source; approve the final notice policy/wording; separately authorize any staging migration and account/API scope; qualify actual D1 transactional/RETURNING behavior and a provider's definitive rejection/rate-limit/idempotency contract; review emergency disablement and ambiguity reconciliation; and run staging fault acceptance. This proposal and its source acceptance authorize no live migration, publication, post or enablement.
